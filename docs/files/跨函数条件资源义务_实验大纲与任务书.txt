面向跨函数条件资源义务的软件缺陷检测实验大纲与任务书
V1.0  条件立项版 2026年11月25日


一 研究决策与工作边界

建议以 BugAuditor 的公开实现为起点，先开展两周左右的立项验证，研究跨函数资源管理中“何时产生释放义务、责任如何转移、何时真正履行”的学习与组合。第一阶段只做资源泄漏；引用计数泄漏作为通过首轮验证后的扩展。暂定英文题目为 Learning Guarded Responsibility Transfers for Compositional Resource Leak Detection。题目是研究命题，不是已获证实的贡献。

本任务书按两张 RTX 3090 设计。已确认的是 GPU 条件；服务器系统、CPU、内存、磁盘、模型 API 预算和第二标注者尚未确认。当前任务仅完成研究规划，不表示已复现基线、构建数据、训练模型或取得检测增益。所有样本规模、阈值与工期均为建议预案。

目标任务是仓库级 C/C++ 资源缺陷检测及证据定位，不沿用原 LLDP 的文件内行排序协议。首个实现优先 C 和 C++ 中显式释放、直接调用、有限调用链的子集；C++ 析构与 RAII、回调、间接调用、并发与跨线程所有权作为明确的边界条件，不能忽略后仍宣称覆盖完整 C++。

对新颖性的当前判断是“有明确问题依据、值得小规模验证，尚未通过最终新颖性审查”。不能保证顶刊录用或所谓保底分区。能做的是把已有思想剥离，把剩余机制写成可反驳假设，并在大规模投入前设置淘汰门槛。尤其需要补读 AROP 全文，以及核对 POM、LAMeD、资源规范推断的细粒度机制。

立项要回答的核心问题

在缺少完整 API 规范、存在项目自定义封装时，能否从防御代码与合法例外中学习带程序证据的条件责任关系，并在新调用组合中正确传递未履行义务？判断依据必须同时包括检出真实泄漏、排除合法转移，以及对未见组合的泛化。单纯增加上下文或更换基础模型不能回答这个问题。

当前可启动 | 后续依赖 | 本轮交付
文献差异审查与基线环境核查 | 直接竞争机制核清后再做大规模训练 | 实验任务书与任务清单
小样本人工证据审计 | 真实数据冻结后再做确认性比较 | 明确输入 输出 验收与停止条件


二 选定基线与问题证据

主基线 BugAuditor

BugAuditor 发表于 USENIX Security 2026，具有公开论文与仓库。[1][2] 论文第 7.2 节从 675 份报告中排除了 253 份跨函数责任不清的报告；这些不是 253 个已证实漏洞或漏报。第 8 节也讨论了跨函数上下文等局限。其现有提示已考虑触发条件、等价防御和资源逃逸，因此研究缺口不能表述为“它完全不理解条件或上下文”。

实施前固定代码版本：fee4696ee840266c5a10e430b22a63f73d03d004。已有阅读定位包括 prompts/defensive_pattern_reasoning.txt、prompts/bug_detection_inconsistency_auditing.txt、scripts/core/bug_auditing.py 与 AE.md。将改动限制在摘要抽取、责任组合和证据验证接口；防御种子采集、项目解析与候选检索先尽量复用。代码冻结与实际可运行性仍须在服务器上验证。[2]

需要检验的工程假设是：自然语言规则与局部“逃逸后不报”的判断，可能丢失某个具体对象、返回值条件和接手方后续清理之间的关系。它可能导致漏报，也可能导致误报；方向与比例须由独立案例审计决定，不先写成事实。

复现必须区分两种结果

官方 AE 中的已知案例是复现材料，不是无偏测试集。参考输出重放只证明读取或拷贝流程；活跑模型、记录请求和响应，才是执行复现。已知命中案例上的覆盖率不能解释为一般检出率。官方未完整公开的跨函数报告，不能假设可直接取得，也不能由数字反推标签。[2]

备选实现与支撑

RepoAudit 是 ICML 2025 的开源仓库审计系统，已包含按需探索、数据流事实与路径验证。[3] 作为第二个可运行基线，冻结版本 160f5bcd378a02a2417e32e999f93ef5fa0f5e64。它是独立比较对象，也可用于判断结果是否仅依赖 BugAuditor 的候选生成方式。

若 BugAuditor 在五个工作日内仍无法活跑，保留失败日志与原因，先用 RepoAudit 验证数据和机制；切换实现不能等同于证实原文献缺口，也不能把复现失败当作基线性能为零。

拟争取的机制贡献

候选贡献 C1：从含有效防御与合法例外的项目代码中，联合推断“路径条件—资源身份—责任主体—所需动作”的关系式摘要，并以明确的责任残余状态组合调用链。研究重点是弱证据下怎样避免把借用、转移和释放混为一类，以及怎样保留条件与对象之间的关联。关系式摘要在程序分析中有先例，贡献不能仅是设计一个元组。

候选贡献 C2：针对摘要矛盾生成最小证据问题，只细化造成冲突的条件或别名关系；用经过验证的上下文对照约束摘要在语义改变时变化、在等价改写时稳定。这是针对本问题的候选学习与细化机制；反例引导、对比学习与程序变换本身都不是新概念。

候选贡献 C3：建立按项目、API 家族和调用组合分离的真实程序证据基准，检验新组合上的义务传递。数据和评测只能作为支撑，不能在算法无实质增量时替代用户所要求的算法贡献。

G0 新颖性门槛

每篇直接竞争工作完成一行“原文位置—代码位置—输入监督—摘要字段—组合规则—异常返回—未知处理—实验重叠”的证据表。只有至少一个可实现、可观察、不可被现有机制直接覆盖的差异成立，才进入大实验。AROP 全文未核清前只能条件立项；不能以找不到全文或代码证明自己的首创性。

如果 C1 和 C2 只是经典关系分析或规范推断的工程接线，应停止顶刊级算法创新表述。可保留复现与数据审计成果，重新选题；不要靠更名、堆模块或换更大模型挽救创新性。


四 任务定义与最小机制

输入 输出与错误判定

输入为冻结的仓库快照、可解析函数与直接调用边、可见的项目 API 实现，以及统一的候选资源集合。输出为资源泄漏候选与证据链，或者在给定范围内未发现违反，或者分析未知。未发现违反不等于证明全程序安全。每条报警必须带资源创建、责任变化、相关分支及未履行边界的位置。

义务 O 定义为 (r, a, h, g, d, E)：r 为资源及别名身份，a 为必须完成的动作，h 为当前责任主体，g 为成立条件，d 为生命周期边界，E 为源码证据。函数摘要记录条件化 acquire、borrow、transfer、discharge 事件，并分别标注已证实、可能、未知。模型置信分数不能替代程序证据。

一个应当区分的例子

p = make_item();
if (!p) return ERR;
ret = register_item(ctx, p);
if (ret < 0) return ret;  // 若失败不接手，则这里泄漏
return OK;

待验证契约：ret == 0 时转移给 ctx；ret < 0 时仍由调用方负责。

register_item 发生逃逸或写入字段，并不足以证明义务已履行。反之，如果其失败分支内部已释放 p，再由调用方释放会错误。该示例是说明机制的人工例子，不是新发现缺陷。成功条件转移本身是既有概念；需要研究的是如何由证据学得关系并可靠组合。

组合规则与约束

对调用点先做实参替换与别名映射，再把调用路径条件与被调函数守卫合取。acquire 新建未履行义务；borrow 不改变主体；transfer 仅在成立条件下改变主体，不能删除全局义务；discharge 仅在资源身份和动作匹配时消除义务。合流保留条件分支的关联，不能把“可能转移过”合并成“所有路径都转移”。

R[r,h] 表示资源 r 仍由 h 负责的条件
转移条件 t = 调用条件 AND 已验证的被调守卫
moved = old(R[r,h]) AND t
R[r,h] = old(R[r,h]) AND NOT t
R[r,h2] = old(R[r,h2]) OR moved
释放条件 u 成立时：R[r,h] = old(R[r,h]) AND NOT u

上述布尔写法只是单义务说明。首轮不把它直接用于任意共享引用计数；引用计数扩展需要将每次 get 形成的责任令牌分别建模，并检验 put 归属。递归、别名不确定和守卫爆炸时采用有限展开与未知摘要，所有退化都写入日志，不静默判安全。

最小实现路径

用现有解析器定位函数、调用、返回、字段写入和分支；小模型或 LLM 提议结构化摘要；确定性规则核对变量、调用边和控制位置；在有可靠编码的条件片段内调用求解器；组合器传播义务；证据不足时提出一个具体补充查询。首版每个候选最多两轮细化，超过即未知。求解器只验证编码后的命题，不自动证明 LLM 生成的前提正确。


五 研究问题与预注册假设

问题 | 可反驳假设 | 主要证据
RQ1 机制是否有效 | 同模型 同候选 同预算时优于扩上下文和普通摘要 | 真实已确认泄漏的检出差与误报约束
RQ2 是否学到语义关系 | 关键条件变更引起正确改变 等价变换保持判断 | 配对正确率 守卫与主体准确度
RQ3 能否组合泛化 | 未见项目 API 家族或调用组合仍有收益 | 分组隔离测试与调用深度分层
RQ4 是否实用且可解释 | 收益具有合理成本 且报警证据可人工核验 | 扫描精度 成本 覆盖率 证据完整度
RQ5 训练是否必要 | 专门学习比同基础模型结构提示有额外收益 | 不训练 普通微调 完整学习的匹配比较

预注册主终点为：冻结测试集上、固定推理预算下的在范围内已确认缺陷检出率差。共同约束为报警精度不明显降低，并报告未知率及解析覆盖率。确认性样本量和最小有意义差异在先导结束后根据配对不一致率确定，不能用测试结果反向选主指标。

初始工程决策阈值建议：相对最强上下文或摘要对照，检出率提高至少 10 个百分点；报警精度下降不超过 3 个百分点；推理 token 不超过该对照的 1.5 倍。它们是是否投入后续研究的暂定门槛，不是统计显著性标准，也不是投稿录用标准。先导后允许在不看冻结测试的前提下调整一次，并留变更记录。

若 200—300 个证据实例仍不足以形成足够的配对不一致缺陷，就增加独立真实项目或缩小结论，不能用大量近重复变体补足有效样本量。对局部子集提升明显但整体不稳定的情况，论文主张必须限定为该子集。


六 数据构建与防止评测失真

四类材料分别使用

材料 | 建议规模与用途 | 不能作出的解释
官方 AE 材料 | 按公开范围复现 原始结果核对 | 不能报告一般召回率
独立先导材料 | 约 60 个上下文 约 2 个项目 | 不能继续兼作冻结测试
真实确认性材料 | 目标 120 个缺陷与 120 个合法上下文 来自至少 6 个测试项目 | 不是全仓库缺陷总量的完备真值
机制对照材料 | 约 80 至 120 对 由训练或开发侧独立构造并审查 | 不能替代真实缺陷证据

规模是目标而非已取得资源。先导应包含责任转移成功、转移失败、被调方清理、借用、包装释放和路径不可达等情形，避免只挑缺释放的简单正例。独立确认性数据优先从公开修复提交、回归测试和问题讨论交叉核实。候选项目可包括 curl、libxml2、libpng、OpenSSL、libarchive、FFmpeg；Linux 作为额外外部验证。清单需经可解析性、许可、缺陷证据和家族独立性核查后冻结，不能按本方法表现挑选。

每个实例的证据包

保存项目 URL、缺陷前后 commit、父版本、构建配置、相关函数闭包、API 契约出处、触发路径、资源与主体变化、修复理由、可接受定位锚点、标注者和争议记录。补丁删除或新增的一行不是充分真值；必须说明为什么在旧版本上违反义务，并验证补丁确实针对该问题。克隆、回移和同根因多补丁建立 lineage_id，统计按根因去重。

合法上下文不能用“没有 issue”直接标成安全。需要完整的局部责任闭环、可核验的转移契约或有效释放证据。无法确认者标为 unresolved，单独公布数量。评价范围限于指定资源与生命周期，不宣称整个函数没有其他缺陷。

隔离协议

先导项目与最终确认测试分开。默认冻结至少 6 个独立测试项目；若训练模型，则另用约 3 至 4 个训练项目和 1 至 2 个开发项目，总项目数量需随可用数据调整。项目同源分叉、依赖拷贝及修复回移进入同一组，不能随机打散函数。训练、验证、测试的补丁和近重复切片在 tokenizer 或 AST 指纹上检查并人工抽查。

组合泛化测试单独定义：训练可以见过 acquire、borrow、transfer、discharge 各原子效应，但测试中的效应次序、返回条件与责任主体组合不能出现在训练组合中。再做严格的 API 家族隔离。两种泛化难度分别报告，不能把 API 改名当作未见 API 泛化。

时间分割用于降低公开补丁记忆风险，但无法证明预训练未见过样本；记录模型发布时间、可知训练截止与提交日期，增加较新快照外部扫描及去标识敏感性分析。重命名稳健性只是诊断，不能证明没有污染。

双人标注与预算

建议每例两人独立审阅关键标签，由第三方或导师裁定争议；报告原始一致率与适当一致性统计，并保留未解决项。预估完整证据标注可能需要 200 至 400 人时，必须由先导计时修正。若只有一名研究者，应安排部分独立复核；在没有独立标注支撑前降低真值与机制正确性主张。


七 模型与程序分析实现大纲

第一版先验证组合机制

M0 复用基线候选生成与上下文检索，不训练。M1 将原有文本式推断改为 JSON 结构化效应提议，但仍由统一模型生成。M2 加入带守卫的责任组合器和未知状态。M3 才增加证据冲突驱动的摘要细化。只有 M2 或 M3 对强上下文对照产生明确增益，才投入专门模型训练。避免把训练成本当作新颖性。

最少模块为 frontend、summary、compose、audit、evaluate。frontend 尽量复用基线 Joern 或已可用的解析流程，不同时维护多个前端。summary 保存事件、守卫、对象、责任、证据行和验证状态；compose 做实参替换、条件组合和有限展开；audit 输出证据与 unknown 原因；evaluate 从不可变预测文件计算结果。

证据验证与反例细化

验证分三层：结构层检查 JSON、变量引用、调用边与源码范围；关系层检查守卫分支、返回值和别名映射是否有来源；路径层只对已正确编码的条件调用求解器。SAT 仅说明公式可满足，不证明真实路径可执行；UNSAT 也不能替错误或漏掉的语义假设背书。无法支持的模型提议必须保留为未知或假设。

发现矛盾后定位最小冲突片段，例如“同一失败返回下，摘要同时声称已接手与未接手”。仅请求其相关分支、返回或被调实现，重新生成受影响字段；每例最多两轮细化，超过预算结束为未知。冻结统一问题模板与停止规则，不能看测试标签后人工追问直到答案正确。

可选神经模型与训练目标

首选约 7B 量级代码模型作结构化摘要器，以仓库内真实源码提议条件效应。正式选型时核验官方权重、许可证和显存实测，不把具体模型热度当作贡献。单卡先做 4 bit QLoRA 可行性探针，短上下文起步；两卡分别运行训练与独立评估或不同随机种子。两张 24 GB 卡不能直接视为一块连续 48 GB 显存。

训练标签来自训练项目内人工确认的摘要及有程序证据的自动样本，自动样本记录验证级别，不把 LLM 自评当真值。建议先准备 200 至 400 个高质量函数摘要，再视覆盖率扩至约 2000 至 5000 个弱监督或半自动样本；若证据不足，不扩量。

L = L_struct + lambda_cf * L_pair + lambda_comp * L_comp
L_struct：条件效应结构的监督损失
L_pair：经验证的语义变更对与等价对约束
L_comp：可验证调用组合的责任一致性约束

L_pair 可用长度归一化序列得分：语义改变对使正确摘要比“沿用原摘要”高出预设 margin；等价对约束守卫与责任字段一致。L_comp 在可微版本中使用正确组合与错误组合的判别损失；非可微的组合器只产生可验证的训练对和错误反馈，不能宣称直接反向传播经过 SMT。权重仅在开发集以 0、0.1、0.5、1 的小网格选择。

必须比较相同基础模型的结构提示、仅 L_struct、加入 L_pair、加入 L_comp 和完整目标，且训练数据量与步数匹配。若只是多训练数据带来收益，贡献应归于数据而非组合目标。若无训练版本足够好，可把论文定位为程序分析方法，删除无收益的神经模块。

最低限度实现检查

用小程序验证正常释放、成功转移、失败不转移、失败内部释放、借用、包装释放、别名指向错误资源、不可达路径与未知调用。检查器至少要能拒绝缺少源码证据的 discharge，不能把未知自动转成安全。引用计数扩展另加多次 get 与不匹配 put 检查。


八 详细实验矩阵

E0 先验证问题是否值得做

在独立先导约 60 个上下文上，活跑 BugAuditor 与统一模型的扩上下文版本。对失败盲审分类：候选未生成、项目 API 不识别、责任主体错误、条件混淆、等价释放未识别、路径错误、解析或预算失败。记录每类计数与证据，不从论文限制直接推断这些错误一定在自己的数据中存在。若跨函数责任错误很少，或者扩上下文已解决，暂停原算法立项。

E1 主效果与真正的竞争对象

组别 | 具体设置 | 排除的替代解释
B0 | 官方方法与可复现配置 | 原始起点
B1 | 相同模型 增加调用上下文 | 只是上下文不足
B2 | 相同模型 自然语言函数摘要与缓存 | 只是摘要或缓存有效
B3 | 相同模型 结构化摘要 无责任组合器 | 只是输出格式有效
O1 | 带守卫责任组合 无迭代细化 | 核心组合机制
O2 | 完整组合 加证据冲突细化 | 细化带来的额外收益
N1 | 通过门槛后加入专门训练 | 学习目标是否必要

对 B1、B2、B3 使用相同的函数检索权限、候选集合、可见源码、基础模型版本与总 token 上限。另绘制预算曲线，让原方法也能用更多上下文；上下文窗口不允许时使用相同分块策略。摘要生成和缓存预处理成本都计入冷启动结果，不能只报复用后的成本。

外部工具至少包括 RepoAudit 与一个可运行静态分析器，建议 Infer 或 Clang Static Analyzer；确认支持的泄漏类别与版本后冻结。LAMeD 的公开流水线[13]可行时加入“生成注解加静态分析”对照。[8] POM 按支持的缺陷类型做机制和适用性比较，不把其 UAF 或 double-free 结果强行转换为泄漏成绩。[6]

SpecAuditor 涉及补丁与文档规范来源，应在同样可见输入条件下比较适用子集。[5] AROP 必须补读并调查代码；若无法取得可执行实现，只作可核验的方法差异对照，披露缺失，不能自制弱化版本然后冠以原方法名称。[4] LLMDFA 与 Java 资源检查器主要用于机制比较，除非建立合理同语言同任务适配。[7][9][10][11]

E2 语义对照与机制正确性

为相同局部调用分别提供合法接手与失败不接手的真实上下文，尽量保持局部 token 分布接近；再增加守卫反转、借用改接手、被调清理迁移等受控变化。每对必须有函数闭包、编译或相应静态证据，能运行时补充故障注入与回归测试。合法语义必须人工核对；编译通过本身不能证明变换有效。

加入重命名、无关语句变化、等价 wrapper 等保持目标义务不变的对照。报告两成员都正确的 pair accuracy、原预测不变率及适当改变率；不能只用“预测翻转”充当理解正确。合成对仅解释机制，最终结论仍以独立真实缺陷为准。

E3 泛化与难度分层

分别做未见项目、未见 API 家族、未见调用组合测试；按调用深度 1、2、3、4 及以上，资源封装层数、错误路径数量和守卫复杂度分层。测试组合的定义和分组脚本冻结。少量样本的分层只作描述，不凭偶然大幅提升宣称泛化。

E4 消融与性能归因

依次去掉守卫关联、责任转移、别名映射、结构化效应、细化机制与训练约束；保持输入与预算一致。去掉守卫时不能同时减少检索上下文，去掉训练损失时不能同时改变数据量。再用人工正确摘要运行组合器，估计抽取误差与组合器误差各占多少；这只是诊断上限，不与自动系统混排名。

E5 自然分布扫描与成本

在从未用于调参的新快照上做限范围的全仓库扫描。人工审查全部报警，或按事先设定概率抽样并加权估计精度。报告独立根因、重复报告、未解决报警、每个真阳性的总成本、峰值显存、CPU 预处理和总时长。全仓库总缺陷数未知时，只报告精度与发现数，不报告全仓库召回。

新的缺陷由内部复核形成证据包。向维护者发消息、提交 issue 或补丁属于后续明确授权的工作，不在本次规划中执行；维护者尚未回复的候选不能写成已确认。


九 指标 统计与实验冻结

主要指标与分母

已知缺陷检出率 = 被正确报警的在范围内独立缺陷数 / 冻结的在范围内独立缺陷总数。对于范围内案例，候选未生成、超时或未知均不能从分母中剔除。范围外资格在看预测前按统一规则确定，并公布被排除数量与原因。端到端结果和共享候选条件下的审计结果分开报告。

报警精度 = 经核验的真实缺陷报警 / 所有去重报警。未解决报警同时报告“只计已确认真阳性的保守下界”和“未解决全为真时的上界”，避免只对易确认报告计算精度。配对合法样本上的 specificity 单独报告，不能冒充真实扫描精度。

证据定位采用资源创建点、关键转移或失败分支、未履行生命周期边界的可接受锚点集合；报告证据链正确率、覆盖的锚点比例和人工审阅函数或行数。可选 Top-k 行命中必须为所有方法提供相同候选行域与预算，并公布漏检案例处理规则。注意力权重不自动等于定位证据。

统计与实践效应

建议在开发阶段把检出率提升 10 个百分点、精度下降不超过 3 个百分点作为继续投入的参考效应，不把它们写成必达结果或顶刊标准。依据先导中配对不一致案例数量做功效或置信区间宽度模拟，再冻结最终样本量和最小有意义差异。不能测试后重新挑阈值。

比较按相同实例配对。主要报告差值、置信区间、每项目结果与 win/tie/loss；按项目和缺陷谱系做分层或聚类 bootstrap，项目很少时强调区间不稳定。二元检出可补充配对检验；大量次级检验采用预先规定的多重比较控制。不得把同一缺陷的多个变体当成独立统计样本。

本地训练至少 3 个随机种子；推理在代表性子集上至少 3 次重复，并对核心比较尽量重复完整运行。即使 temperature 为 0，也记录服务版本与可知非确定性。全部试验都有 run_id，失败、超时与中止均保留，不能只取最佳一次。

冻结与审计

冻结数据版本及 hash、代码 commit、模型权重或服务版本、提示文本、采样参数、种子、候选清单、检索深度、token 与时间上限、去重规则、评价脚本和主次终点。确认测试只在冻结后执行；若修复实现 bug，需要记录解冻原因并对所有受影响方法一致重跑，原始结果保留。

未来安排独立复核者审查随机样本、结果表分母与关键源码证据。当前没有执行独立审计；不能将自行检查命名为独立审计通过。

双 3090 与预算安排

本地优先：先验证基础模型推理与短上下文 QLoRA 的显存和吞吐，不把大模型全参数训练列为目标。初始训练探针不超过 4 GPU 小时；开发训练暂按 48 GPU 小时预留，正式训练与确认实验根据实测估算后冻结。这里的上限是建议资源规划，不是已使用时长或已获服务器执行许可。

建议统一从每候选 4k、8k、16k 输入 token 三级预算做开发探针，模型上下文不足则等比例缩减；把提示、摘要生成、检索后重复输入、输出、验证与重试全部计入总预算。正式主预算依据开发侧可行性冻结，各方法必须一致，另报告预算曲线。

API 预算未确认，本方案默认本地可运行路线；若为复现原配置需要商业模型，先用官方参考结果核对数据流并记录“未活跑原模型”，不能把替换本地模型称为原设置复现。费用估计公式为项目数乘候选数乘每例总调用成本，并计入重复与失败；价格需执行前按官方页面重新核验。

预处理的 CPU、RAM 和磁盘可能比 GPU 更先成为瓶颈，T02 必须实测小项目的索引大小与峰值内存，再决定是否运行 Linux。不能把“有双卡”理解为已满足全量内核分析条件。

十二 顶刊级论文应具备的证据

TSE、TOSEM 或 ICSE、FSE 等可以作为贡献规模的参照，不构成录用承诺。本任务书不对未来 JCR 或中科院分区作保底判断。真正需要争取的是下列证据同时成立，而不是某个单项指标超过一个预设数字。

算法证据：明确说明既有规范推断、关系摘要与反例细化不能直接解决什么，给出新机制的操作定义和与先例的逐项差异。能说明适用假设、关键不变量与复杂度；证明仅在所建模子集内有效，不能把 LLM 提议称为全程序健全性证明。

归因证据：相同基础模型、可见代码和预算下，完整方法胜过扩上下文、普通摘要和结构化提示；去掉新机制后关键收益消失。

真实效果：多个独立项目有真实缺陷和合法例外，未知与未覆盖不隐藏；最好有新快照发现及外部确认，但确认数量不能代替算法创新。

泛化证据：未见项目、API 家族与调用组合分开检验，能够解释成功与失败的边界；不能只在同一内核的多个子目录上声称跨项目。

可复核证据：源码、数据谱系、标签证据、提示和运行日志可追溯，主要表格能从原始文件重算；公开许可证允许的材料，不能公开的说明替代获取方式。

不能作为顶刊创新主张的结果

仅增加调用深度、改提示词、换强模型、加入现成 SMT、把资源操作写成元组、在若干已知命中样例上达到高覆盖，均不足以单独支持本选题的算法创新。若只有合成对改善，真实数据无增益，或者原方法加上下文已达到相同结果，应调整或停止投稿定位。

论文主张台账建议使用 claim_id、准确表述、对应实验、原始文件、反例与边界、当前状态六列。状态只允许待验证、已支持、部分支持、被否定。新颖性、准确率和成本的空白项不能在写作时补成确定语气。


十三 首轮两周的具体执行顺序

第 1 天：固定新项目范围与排除项，完成服务器规格记录，下载并固定 BugAuditor、RepoAudit 的版本。先读 AROP、POM、LAMeD 与资源规范推断，列出尚未核清的机制。

第 2 至 3 天：完成最小活跑与参考重放区分；建立前 10 个先导证据实例，记录人工审阅时间与上下文闭包。不要开始模型微调。

第 4 至 5 天：完成第一版新颖性证据表；先导扩大到约 30 例，活跑原基线与扩上下文控制。若缺口仅是调用上下文不足，在本周结束时重新定题。

第 6 至 8 天：先导向约 60 例推进，独立复核典型错误与合法例外；写出结构化效应模式，在人工正确摘要上检查责任组合规则。

第 9 至 10 天：汇总失败分布、基线运行成本、可标注性与机制差异；提交 2 至 3 页立项审查单，决策继续、缩小范围或转向，并据此开启下一窗口。

两周验收不是“已经获得顶刊结果”，而是能够明确回答：新机制相对哪些工作新增了什么；错误是否真实且足够普遍；普通上下文办法为何不够；程序证据能否获得；后续数据与计算成本是否可承受。五项缺一，都不宜直接进入全量训练。
